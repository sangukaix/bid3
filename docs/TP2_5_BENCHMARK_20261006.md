# TP2-5 벤치마킹: BID3 적용 후보

확인일: 2026-10-06. 대상은 현재 개인 PC에 복원된 OLIGO-K/TP2-5 소스다.
TP2-5와 BID3 서비스·모델 설정·사용자 자료는 변경하지 않았다.
이 문서는 코드 비교와 선택한 오프라인 검사 결과이며, 실제 모델 생성 품질 비교는 아니다.

## 결론

가져올 가치가 가장 큰 것은 생성 후 검수/보완, 폰트 폭에 근거한 PPT 텍스트 배치,
근거 입력의 무손실 압축, 출처 추적, 저장된 요청의 복구다.
TP2-5의 관광 전용 구조나 유료 최종 승인 정책을 그대로 이식하지 않는다.
BID3의 기존 입찰 기능에도 유사 기능이 있으므로 발표자료 작업실에 연결할 부분부터 진행한다.

## 1. 생성 → 코드 검사 → 검수 → 한 번 보완

TP2-5 근거:
- `ai_server/app/agents/report_orchestrator.py:489`: 작성본 코드 검사와 Reviewer 연결.
- 같은 파일 `:509`: 미승인 초안의 보완과 재검수.
- `ai_server/app/agents/plan_quality_gate.py:98`: 등록 출처, 필수 항목, 실행 단계 등의 결정적 검사.
- 같은 파일 `:216`: 모델의 승인과 코드 검사를 결합. 코드의 중대 문제를 AI 승인으로 덮지 않음.

BID3 상태:
- 입찰의 `server/bids/services/rag/proposal.py`에는 요구사항 대조·회사 주장 검토·PPT 파일 검사가 있다.
- 발표자료 `server/presentation_studio/workflow.py:61`은 페이지 범위·잠금·버전 충돌을 검사한다.
- 발표자료에는 본문 작성 뒤 내용 품질을 검수하고 해당 문제만 보완하는 단계가 없다.

적용안:
발표자료에 페이지별 누락·중복·미제공 수치·출처·글자 넘침 점검 결과를 만든다.
자동 보완은 최대 한 번, 수정 허용 페이지/상자에만 적용하고 잠긴 페이지는 기존 검증을 유지한다.
검수는 기본 Gemma4로 별도 요청한다. 같은 모델의 재검토가 독립된 정확성 보증은 아니다.
입찰과 일반 발표에 동일한 필수 예산/KPI/5단계를 강요하지 않는다.
사용자 instruction과 작성 목적에 따라 검사 항목을 정한다.

## 2. 글자 수 추정 대신 실제 폰트 폭과 페이지 공간 검사

TP2-5 근거:
- `ai_server/app/proposal_layout_v7.py:38`: 설치 폰트 로딩.
- 같은 파일 `:51`, `:99`: 폭 기반 줄바꿈, 글자 크기 조정, 표시 공간 초과 시 오류.
- `ai_server/app/proposal_slide_content.py:206`, `:220`: 출처 원문을 보존하며 열·페이지로 나눔.

BID3 상태:
- 입찰 `server/bids/services/proposal_text_fit.py:36`은 긴 문구만 모델로 줄이는 제한된 보완을 제공한다.
- 발표자료 `server/presentation_studio/ai.py:118`은 면적/글자 크기에서 max_chars를 추정한다.
- 현재 발표자료 적용 작업은 이 추정에 맞게 썼는지, 렌더된 글자가 넘쳤는지 별도 검사하지 않는다.

적용안:
기존 템플릿의 폰트·텍스트 상자·표 셀의 공간과 여백을 읽고 폭/높이 기반의 보수적 검사로 보강한다.
넘친 상자만 요약/줄바꿈/허용 범위 내 크기 조정 후보를 만든다.
수치·날짜·부정·미확인 조건을 보존하고, 그래도 부족하면 사용자에게 분할을 제안한다.
TP2-5의 1600×900 좌표·고정 폰트·최소 크기를 다른 사용자 PPTX에 그대로 적용하지 않는다.
Pillow 측정은 Office와 완전히 같지 않으므로 실제 렌더 검증을 병행한다.

## 3. 무손실 표 압축과 중복 근거 제거

TP2-5 근거:
- `ai_server/app/llm/context_tables.py:27`: 반복 JSON 객체를 열/행 표로 압축.
- 같은 파일 `:46`: 정확한 복원 검사.
- 같은 파일 `:78`: 동일한 긴 원문/객체를 참조로 중복 제거.
- 예약 키 충돌을 escape하고 압축 결과가 작을 때만 사용한다.

BID3 상태:
입찰은 출처가 있는 발췌 패킷을 사용한다. 발표자료는 대화와 참고자료를 예산 안에서 줄이지만
슬라이드 텍스트를 상자당 400자·65상자로 제한하고, 자료별 일부 발췌를 사용한다.
이는 전체 원문을 읽었다는 의미가 아니다.

오프라인 비교:
- 기존 합성 5쪽 PPTX를 발표자료의 `compact_slide` 형식으로 변환한 입력을 사용했다.
- 동일한 compact JSON 기준 4,388 → 2,798 UTF-8 bytes, **36.2% 감소**.
- TP2-5 `decode_tables`로 복원한 값과 원본의 완전 일치를 확인했다.
- 실제 요청은 현재 페이지/자료 구성이 달라 동일한 감소율을 보장하지 않는다.
- bytes 감소는 추론 시간·GPU 메모리·작성 품질의 개선 측정이 아니다.

적용안:
우선 반복 텍스트 상자/근거 구조에 작은 범위로 적용하고 전체 값·타입·출처를 복원 검증한다.
Gemma에 표/참조 해석 규칙을 전달하고 기존 방식과 실제 생성 결과를 비교한다.
압축이 자료 발췌·입력 생략 문제를 자동 해결하지는 않는다.

## 4. 페이지별 출처와 사실/가정 구분

TP2-5 근거:
- `ai_server/app/agents/plan_quality_gate.py`: 미등록 source_id와 미승인 성과 인용 검사.
- `ai_server/app/proposal_slide_content.py:278`: 슬라이드 노트에 근거 기록.
- `ai_server/app/proposal_presentation_v4.py:829`: 샘플 문구·필수 구조·네이티브 표/차트 검사.

적용안:
발표자료 작성 결과에 사용한 파일/URL·발췌 위치·자료 버전을 페이지별로 남긴다.
‘실제 구현/측정’, ‘사용자 제공 주장’, ‘목표/계획’을 구분하고 필요 시 출처 슬라이드·노트를 만든다.
현재 sources 표시는 AI 요청에 전달된 자료 목록이지 페이지별 주장 근거의 검증 결과가 아니다.
입찰의 기존 출처/요구사항 검사를 재사용하되 일반 발표의 개인 설명을 공식 문서처럼 취급하지 않는다.

## 5. 요청 복구와 단계별 기록

TP2-5 근거:
- `ai_server/app/strategy_store.py:120`: 요청·상태 저장.
- 같은 파일 `:197`: 중단 작업 조회.
- `ai_server/app/main.py:148`: 서버 시작 시 저장 요청 재개. 사라진 일회성 첨부나 BYOK 세션은 재개하지 않음.

BID3 상태:
발표자료 Job을 DB에 저장하고 별도 작업 프로세스를 실행한다. 브라우저/API 재시작만으로 작업이 중단되지는 않는다.
PC 종료로 작업 프로세스가 사라진 경우에는 현재 수동 취소 후 재요청이 필요하다.

적용안:
worker heartbeat·요청 당시 모델/지침/자료 hash·단계 상태를 기록한다.
중단을 감지하고 원본 버전과 자료가 일치할 때 재요청/재개를 제공한다.
TP2-5의 복구는 저장 요청의 재실행이며, 작성된 각 슬라이드부터 이어가는 checkpoint와 같지 않다.
BID3에서 페이지 checkpoint를 도입하면 취소/동시 수정/중복 저장 경계까지 별도 검증한다.

## 6. 저장 내용으로 출력, 캐시 검증, 실패 분리

TP2-5 근거:
- `ai_server/app/proposal_presentation_v4.py:850`: 저장 report로 PPTX 출력. 다운로드마다 새 LLM 생성 불필요.
- `ai_server/app/proposal_preview.py:137`: 보고서+레이아웃 버전의 hash로 PDF 캐시 재사용.
- 같은 파일 `:127`: 캐시 임시 파일을 원자 교체. 잘못된 PDF는 다시 생성.

BID3 상태:
발표자료는 이미 버전별 PPTX를 보관하고 동일 파일을 다운로드한다.
Office 변환은 프로세스 간 파일 잠금으로 보호하고 버전별 PNG를 캐시한다.
본문 저장 뒤 미리보기 실패를 분리하는 처리도 있다.

적용안:
같은 파일의 여러 버전/프로젝트 간 파생 미리보기 캐시만 내용 hash+렌더 버전으로 공유할지 검토한다.
완료 marker 전에 페이지 수/파일 정상 여부를 검증하고 임시 디렉터리를 원자 교체한다.
파일 접근 권한은 각 프로젝트 소유자 검사로 계속 제한한다.
TP2-5의 스레드 잠금으로 BID3의 더 강한 프로세스 간 잠금을 대체하지 않는다.

## 그대로 가져오지 않을 부분

- 관광 지역·ML·공간 분석·공식 사례 Schema와 11~12쪽 고정 문서 구조.
- OpenAI/Perplexity 필수 조사·최종 검수 또는 유료 자동 대체.
- `python-pptx`로 전체를 재저장하는 방식을 업로드 원본 보존 엔진의 대체로 사용.
- 기존 5-Agent 전체를 도입해 매 페이지마다 여러 모델을 호출하는 구조.
- LLM 승인 점수를 정확성/제출 가능성 보증으로 표시.

Gemma4 기본과 유료 대체 없는 정책을 유지하며 필요한 검사 단계를 별도 함수/요청으로 구성한다.

## 검증 범위와 권장 순서

TP2-5 자체 가상환경에서 아래 선택 테스트 **20개 통과**:
`python -m unittest ai_server.test_context_tables ai_server.test_proposal_preview ai_server.test_plan_quality_gate`.
네트워크·유료 API·실제 LLM·Office·서비스 DB 연결 없이 수행한 검사다.
TP2-5 전체 테스트나 최근 Perplexity 연결의 실제 작동을 검증했다는 의미는 아니다.

권장 순서:
1. 실제 학원 PPTX를 기준으로 발표자료 텍스트 배치 검사 + 코드 품질 검사 + 제한된 Gemma 보완.
2. 페이지별 근거 기록과 무손실 압축을 Gemma 기존 입력과 비교 검증.
3. 작업 중단 감지/복구와 내용 hash 캐시를 운영 개선으로 적용.

이번 벤치마킹에서 서비스 기능은 이식하지 않았다. 후속 구현은 실제 파일로 원본 보존·사실 정확성·표시 품질을 비교하면서 진행한다.
