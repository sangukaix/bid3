# 제안서 작성·검수 검증

## 적용한 흐름

공고 요구사항 → 검토 완료·유효 회사 근거 → 평가항목별 작성 설계 → 본문 작성 → 실제 PPTX 읽기 → 요구사항·회사 주장·수치 모순 검수 → 최대 3쪽 1회 보완 → 재검수 순서다. 기존 유지보수 설정의 PROPOSAL·CLAIM_REVIEW를 사용하며 유료 대체 경로를 추가하지 않았다.

작성 계획은 본문, 별도 서식, 자격·증빙, 가격, 담당자 분류 확인으로 나눈다. 보수적인 규칙 분류이므로 원문 대조가 필요하다. 본문 항목에는 수행 방법·담당 역할·일정·산출물·검증 방법과 회사 근거 후보 ID를 연결한다. 한 개의 명시된 배점만 페이지 배분 가중치로 사용하며 합계·범위·복합 배점은 추정하지 않는다. 배분은 원본 양식에 대한 작성 제안이고, 실제 답변 반영은 최종 출력 인용으로 별도 확인한다. 근거 후보 연결은 자격 충족이나 제출 완료가 아니다.

로컬 신규 생성은 작은 양식 칸에서 빠진 세부 답변을 보완하기 위해 작성 계획의 **본문** 조건별 상세 페이지를 추가한다. 기존 페이지는 유지하고, 원문 조건·미래 수행안·담당·일정·산출물·검증 방법·확인 질문을 구분해 편집 가능한 텍스트로 출력한다. 원문 위치는 발표자 노트에 기록한다. 추가 페이지 본문은 12pt로 측정하여 배치하며, 한 칸에 담기 어려운 조건은 자르거나 작은 글자로 줄이지 않는다. 공고에서 검증한 분량 제한과 전체 50쪽 상한을 적용한다. 양식의 목표 장수는 권장 분량이며 상세 답변 때문에 늘어난 경우 별도 검토 문구를 남긴다. 공간·상한으로 배치하지 못한 ID와 이유는 `writing_plan.detail_pages.omitted` 및 작성 계획 안내에 남는다. 미배치는 완료가 아니다.

상세 페이지의 원문 조건 상자는 요구사항 답변 검수에서 제외한다. 원문을 복사한 것만으로 반영됐다고 판정하지 않으며 수행·검증 답변과 남은 질문을 대조하도록 지시한다. 상세 페이지를 해당 요구의 우선 검수 위치로 연결하고, 부분 수정 후에도 작성 계획과 현재 출력 페이지 연결을 유지한다. 전체 회사 주장 검수는 이 원문 상자를 포함하여 모든 텍스트를 읽는다. 숫자 모순 후보에서만 원문 재인용·제목·꼬리말·관리 ID를 제외하여 페이지 번호나 R/K 식별 번호끼리 불필요한 문장 쌍을 만들지 않는다.

모순 검수의 형식 오류는 실패한 묶음에 한해 각 문장 쌍을 한 번씩 재검사한다. 통신 실패를 반복 호출하거나 실패를 완료로 바꾸지 않으며, 재검사도 실패한 쌍은 검수 실패로 남기고 자동 보완을 차단한다. 요구사항 인용에 모델이 검색 발췌의 해시 ID를 붙인 경우 그 앞부분만 제거할 수 있다. 나머지 실제 문구·페이지·수치·단위·미확인 표현은 동일한 대조를 통과해야 한다. 없는 문구나 다른 단위는 여전히 반영 확인으로 처리하지 않는다.

최종 회사 주장 검수는 표·그룹·고정 텍스트와 미수정·추가 페이지를 포함한다. 노트는 제출 본문으로 보지 않는다. 큰 텍스트는 작은 묶음으로 읽는다. 모델이 모든 텍스트 묶음을 분류하되 탐지 누락·오판 가능성이 있다. 직접 입력과 과거 제안서만으로 검토 완료 증빙 판정을 내리지 않는다. 검토된 회사 지식의 내용·원문 발췌와 연속 인용을 대조하며 출처 ID·검토일만 인용한 것은 근거로 인정하지 않는다. 단위·수치·날짜·미확인 표현도 코드로 검사한다.

모순 검수는 숫자가 있는 문장에서 공통 단어가 있고 숫자·단위가 다른 쌍을 대상으로 한다. 실제 인용·페이지가 확인된 후보만 표시한다. 모집단·시점·목표/실적이 다른 경우 모순으로 단정하지 않도록 지시한다. 숫자가 없는 논리 모순이나 차트·이미지의 텍스트, 모든 의미 모순을 탐지하는 기능은 아니다.

보완은 기존 출력의 최대 3쪽을 한 번만 수정한다. 페이지 추가·삭제·다른 페이지/target 수정은 차단한다. 회사 주장·모순에 가중치를 둔 미해결 지표가 감소하고 기존에 확인한 **각 요구사항 ID**가 유지되며 심한 글자 넘침·작은 글씨·양식 안내·미완성 문구 검사가 악화되지 않을 때만 채택한다. 근거 없는 사실을 확인 필요로 바꾸는 것은 위험 감소이며 사실 확인 완료가 아니다. 실패·악화 시 원래 초안을 유지한다. 확정이나 실제 입찰 제출은 자동 수행하지 않는다.

## 웹 사용과 긴 작업

입찰 제안서 화면의 **평가항목별 작성 계획 · 제출 업무**, **최종 문서 전체 AI 검수**에서 확인한다. **현재 파일 전체 AI 검수**는 검수 기록만 갱신하고 파일은 수정하지 않는다. 파일·회사 근거 변경이나 만료 시 저장된 전체 검수는 이전 기록으로 표시한다. **최신 파일 대조**는 저장된 인용의 코드 검사이며 새로운 AI 의미 검수와 다르다.

웹의 새 생성과 전체 검수는 `ProposalTask`에 저장하고 별도 로컬 Python 프로세스에서 처리한다. 브라우저를 닫거나 Django를 다시 시작해도 시작한 작업은 계속된다. 웹 재접속 시 상태·단계·묶음 수를 불러오며 같은 프로젝트의 활성 작업은 한 개다. 실행 중 수정·확정·휴지통 이동을 차단한다. PC/worker 종료 시에는 완료되지 않으며 중단 감지 후 실패로 표시하고 다시 요청할 수 있다. 기존 파일은 보존한다. 분산 서버용 큐는 아니다.

새 환경은 `server\venv\Scripts\python.exe server\manage.py migrate`로 `0024_proposaltask`까지 적용한다. 기존 DB는 먼저 백업한다. 작업 로그·인증 정보·실제 검증 결과는 비공개 `server/media/`, `.local/`에 둔다.

## 반복 가능한 검증

`server/bids/fixtures/proposal_quality_cases.json`에는 교육(R26BK01637158), IT 라이선스(R26BK01635679), 안전진단(R26BK01628456)의 저장된 공고 원문에서 확인한 일부 조건, 수동 예상 판정, 원문 SHA-256·URL·확인일을 기록했다. 시간 단위·계약기간 변경, 증빙 없는 인증 주장, 수치 모순을 의도적으로 넣은 자료이며 실제 제출 제안서가 아니다. 최신 정정공고 확인 여부는 **false**다.

저장소 루트에서 실행한다:

```powershell
cd server
venv\Scripts\python.exe manage.py test --noinput
cd ..
server\venv\Scripts\python.exe server\manage.py evaluate_proposal_quality server/bids/fixtures/proposal_quality_cases.json --output .local/verification/proposal-regression.json
cd web
npm run lint
npm run build
```

회귀 검증은 PROPOSAL·CLAIM_REVIEW가 Ollama일 때만 실행한다. 기대 판정 불일치·검수 실패·수동 기준 미등록 시 결과를 저장하고 실패 종료한다. 입력 파일과 DB는 변경하지 않는다. 기준과 일치했다는 결과를 실제 입찰 전체 품질 점수로 해석하지 않는다.

실제 생성 파일은 비공개 manifest에 다음 형식으로 등록한다. 경로는 manifest 폴더 기준이다. `pptx` 대신 `slides` 문자열 목록을 넣으면 메모리에 검증용 PPTX를 만든다.

```json
{"cases":[{
  "name":"실제 공고 검토 사례", "pptx":"draft.pptx",
  "approved_evidence":"reviewed-company-evidence.txt",
  "source":{"file":"original-rfp.pdf","latest_correction_verified":false},
  "requirements":[{"requirement":"원문에서 확인한 조건","sources":["제안요청서 3쪽"]}],
  "expected":{"requirements":{"R0001":false},
    "claims":[{"text":"검토할 회사 주장","status":"review_required"}],"conflict_count":0}
}]}
```

`approved_evidence`는 담당자가 확인한 근거 텍스트로 원문·조건·유효기간을 보존해야 한다. manifest 표시는 진위나 최신성 인증이 아니다. 실제 제출 검증에는 최신 정정공고, 공고 전체의 수동 기준표, 실제 회사 증빙, 별도 서식·가격, PPTX와 렌더링 PDF의 시각 확인이 추가로 필요하다.

## 2026-10-09 검증 결과

- Django 전체 테스트 **319개 통과**. 소유자 접근, 실제 렌더링 후 전체 페이지 검수, 원본 보존, 회사 근거·파일 변경 시 검수 무효화, 묶음 실패, 단위 불일치, 제한된 보완의 회귀 방지, 작업 중복·실패 복구를 포함한다.
- 프런트엔드 lint·TypeScript·production build, migration 누락 검사 통과. DB 백업 후 0024를 적용했다.
- **gemma4:26b**로 공개 기준 사례 3개의 예상 판정과 일치. 2개 조건의 실제 작성 계획도 생성했다. 기존 13쪽 초안의 격리 복사본은 텍스트 193개, 회사명·담당자 관련 확인 대상 2건, 검수 실패 0건. 등록한 공고 조건 3개는 답변 미확인으로 남았다. 이 조건 3개는 전체 공고의 수동 기준표가 아니다.
- 실제 Gemma 자동 보완 1회·2쪽 시험은 미해결 지표가 5→5로 개선되지 않아 초안을 유지했다. 원본 파일 SHA-256 보존과 기존 확인 조건의 유지도 확인했다. 자동 보완의 품질 향상을 보장하는 결과는 아니다.
- Tailscale 브라우저에서 전체 검수 시작, 작성 계획·최종 검수 결과 표시와 서버 재시작 후 저장 결과 복원을 확인했다. 검증용 계정만 사용했고 작업 후 비활성화·임시 토큰 폐기했다. 실제 회사 근거를 승인하거나 입찰을 제출하지 않았다.
- 검증 호출은 PROPOSAL·CLAIM_REVIEW 모두 Ollama Gemma4였다. OpenAI API는 사용하지 않았다. 실공고 전체 제안서의 신규 생성부터 최종 제출까지 검증한 결과나 상용 서비스와의 동일 조건 품질 비교는 아니다.

## 후속 개선: 공고 조건의 분류와 제출 전 점검

전체 회사 주장 검수에 관련 공고 조건을 최대 3,500바이트로 추가했다. 수행할 교육 인원·회차·기간을 이미 달성한 회사 실적으로 오인하지 않도록 참고하는 자료이며, 회사 증빙과는 분리한다. 공고에 같은 자격이 요구되더라도 회사가 보유했다고 주장한 것은 여전히 검토 완료 근거가 필요하다. 공고 요구사항 목록이 바뀌면 v2 전체 검수 기록도 이전 결과로 표시한다.

`제출 전 점검`은 현재 파일의 본문 인용, 회사 주장·모순 검수의 유효성, 미완성 문구, 분량·출력 문제, 등록된 첨부 읽기 결과를 모아 보여 준다. 별도 서식·증빙·가격·분류 확인 조건과 항상 남겨 두는 담당자 확인 사항도 표시한다. `검수 기록 내려받기`는 파일 SHA-256, 점검 시각, 실제 인용·출처와 검사 결과를 담은 JSON을 저장한다. 소유자만 조회할 수 있고 AI 호출·원문 변경·DB 저장·자동 확정은 없다. 내려받은 기록은 그 시점의 스냅샷이며 제출 가능성 인증이 아니다.

Gemma4:26b로 원문 조건 기반 사례 3개의 수동 예상 판정과 다시 일치했다. 앞선 2쪽 자동 보완 사례는 공고 조건의 오분류가 사라져 가중 미해결 지표 5→3으로 개선됐고, 기존 확인 조건과 레이아웃 검사 보존 후 보완본을 채택했다. 회사 주장·수치 모순 보고는 0건이지만 미반영 계약 조건 1개와 확인 필요 문구 2개는 남는다. 한 사례에서의 개선이며 일반적인 정확도·보완 성공률을 뜻하지 않는다. 실제 사용자 파일은 변경하지 않았다.

후속 코드 검증: Django 전체 **322개**, 웹 lint·TypeScript·production build 통과. 실제 13쪽 격리 파일의 점검 API에서 자동 확인 대상 5개와 가격 조건 1개를 표시했고 파일 해시·DB 변경 시각을 보존했다.

브라우저에서도 자동 점검 5개, 담당자 확인 3개, 부가세 10% 포함 가격 조건의 원문 출처를 확인했다. 실제 `검수 기록 내려받기`로 받은 JSON의 파일 SHA-256이 원본 PPTX와 같고 담당자 확인 사항이 보존됨을 확인했다. 검증용 다운로드는 비공개 QA 폴더로 옮겼다.

같은 출력본의 최종 읽기 전용 검수는 **39쪽, 본문 전용 답변 86개 배치·누락 0개, 작성 설계·검수 기술 실패 0개**였다. 실제 답변 인용은 본문 **74/86개**, 전체 **95/170개**였다. 같은 파일에서도 AI 판정이 변동할 수 있으며 이 수치는 제출 가능성·정확도 점수가 아니다. 회사명 직접 입력의 근거 확인 1건과 모순 비교 경고 10건(비교 관계 미확정 6건)이 남았다. 확인 필요 문구 7개, 기존 작은 본문 2쪽, 반복 상세 레이아웃도 남는다. 전체 사업/교육 기간, 강사 역할, 평가 항목/목차, 발주기관명/참가업체 식별을 혼동한 AI 경고가 실제로 남아 있어, 보고된 모순을 확인된 사실로 받아들이면 안 된다. **초안·검수 보조의 기능 MVP이며, 시험본의 실제 입찰 제출 품질은 계속 미통과다.**

날짜나 일반적인 일정 표현만 같은 문장, 변환 근거 없는 명/class 등의 교차 단위를 후보로 무작정 묶지 않도록 비교 범위를 좁혔다. 숫자·단위·실제 인용 검증은 유지한다. 모순 응답 스키마의 최대 항목 수(5개)에 맞춰 입력 묶음도 최대 5쌍으로 제한하여, 제한된 JSON 응답에서 여섯 번째 후보가 빠질 수 있는 문제를 회귀 검사했다. 이 묶음 크기 변경은 전체 출력 재검수 후 별도 회귀 검사와 실제 Gemma 기준 사례 4개로 확인했다.

39쪽 PDF 전체 축소판과 3·7·10·14·23·39쪽을 확대 확인했다. 23쪽의 본문과 질문이 겹치는 실제 출력 문제를 발견하여, 상세 페이지의 줄 간격을 높이 계산과 같은 절대 pt 값으로 고정했다. 동일 작성 계획으로 비공개 출력본을 다시 만들어 86개 배치·누락 0개를 유지하고, PowerPoint PDF 14·23·39쪽에서 겹침 해소를 확인했다. 실제 사용자 파일이나 기존 저장 제안서를 자동 재작성하지 않았다.

확정 API는 품질 인증이 아니라 명시적 사용자 동작이다. 마지막 격리 파일은 자리표시자·양식 안내·심한 예상 넘침이 0개여서 확정 요청이 200으로 허용됐다. AI 경고 전체가 해소됐다는 뜻이 아니다. 해당 QA 상태는 초안으로 복원했고 파일 SHA를 보존했으며 초안 최종본 다운로드 거절도 다시 확인했다. 실제 회사 증빙, 최신 정정공고, 미정 수행 약속과 별도 제출 서류는 담당자 검토가 필요하다.

줄 간격 수정 후 서버 전체 **358개** 테스트가 통과했다. 격리 검증 계정을 비활성화하고 임시 토큰을 폐기했다. 최신 코드로 API를 다시 실행했으며, OpenAI API 호출 없이 검증을 완료했다.
