# 제안서 서비스 비교와 BID3 적용 기록

확인일: 2026-10-09, Asia/Singapore. 공식 공개 제품·도움말 문서와 BID3 코드를 비교했다.
타 서비스의 유료 생성물을 직접 평가한 결과는 아니며, 공개되지 않은 모델·프롬프트·내부 에이전트 구성을 확인했다고 해석하면 안 된다.
고객 성과·정확도에 관한 공급사 홍보 수치는 BID3의 목표 정확도나 제출 적합성 근거로 사용하지 않는다.

이 기능 비교에서 도출한 설계 제안은 BID3에 대한 판단이다. 각 공급사가 아래의 역할 순서를 그대로 구현한다는 주장은 아니다.

## 이번에 적용한 변경

### 1. 실제 출력물 검수

`server/bids/services/proposal_output_review.py`가 PPTX 본문·그룹·표 셀의 텍스트를 읽는다. 발표자 노트는 제출 본문의 근거로 보지 않는다.
새 제안서의 요구사항 의미 검토는 렌더링 이전 작성 계획이 아니라 **렌더링된 실제 PPTX 전체 페이지**를 입력으로 받는다.
추가한 페이지와 수정하지 않은 페이지도 포함한다. 선택한 기존 PROPOSAL 모델을 사용하며 새 유료 대체 경로를 추가하지 않았다.

요구사항 목록은 로컬·클라우드 모두 저장한다. 검수 인용은 실제 문장·위치와 비교하며,
페이지 삽입 후 인용이 한 곳에서만 발견되면 위치를 다시 연결한다. 문장이 사라졌거나 해당 요구사항 자체가 바뀌면 이전 확인 결과와 집계도 취소한다.
시간·인원·금액 등 수치 단위와 날짜를 대조하고, 미확인·미제공 표현을 확인된 답변으로 인정하지 않는다.
동일한 수의 표기 차이(0.5/0.50, 날짜 앞자리 0)는 허용한다. 단위 환산이나 문장의 의미 전체를 코드만으로 증명하지는 않는다.

### 2. 웹에서 요구사항 대응표 확인

입찰 제안서 작업 화면에 **공고 요구사항 · 최종 파일 대조**를 추가했다.
요구사항, 분류, 우선순위, 평가 배점, 공고 출처, 서식, 실제 답변 인용과 페이지를 표시한다.
확인 필요 문구·첨부 읽기 실패·저장된 분량 제한 초과도 표시한다.
기존 파일에 요구사항 목록이 없으면 전체 반영 여부는 미검수로 표시한다.

**최신 파일 대조**는 저장된 검수 인용과 현재 파일의 대조이며 새로운 AI 의미 검수를 실행하지 않는다.
OpenAI·Ollama 호출이 없고 PPTX 바이트를 수정하지 않는다. 새 답변의 의미 확인은 새 생성의 검수 단계 또는 담당자의 원문 검토가 필요하다.
동시에 수정·확정한 경우 오래된 대조 결과로 덮어쓰지 않도록 변경 시각과 파일을 비교한다.
수정 적용과 최종 확정 때도 현재 파일의 대조 결과를 갱신한다. 새 의미 검토 결과로 자동 확정하는 절차는 추가하지 않았다.

### 3. 공고 원문 캐시와 중복 제거

요구사항 목록 캐시 v5는 원문의 내용·위치·출처 서명을 비교한다.
검색 인덱스가 이전 페이지를 가리켜도 등록된 파일의 현재 전체 페이지를 읽어, 추가·삭제한 페이지를 반영하고 읽지 못한 원문은 오래된 chunk로 대체하지 않는다.
현재 등록되지 않은 신규 첨부나 수정 공고 자체를 찾아오는 기능은 이 변경의 범위 밖이다.
내용이 같은 개별 분석 묶음은 기존 v4 묶음 캐시를 재사용한다. 묶음의 추출 프롬프트가 달라진 것은 아니다.
중복 제거는 소수점·범위·우선순위·배점·서식 차이를 보존한다. 1.5시간/15시간, 3~5회/35회처럼 다른 조건을 합치지 않는다.

## 제출 수준으로 높이기 위한 다음 구현

1. **승인된 회사 근거 보관함**: 실적증명·인력 경력·인증의 원문 위치, 담당자, 검토일과 유효기간을 관리한다. 과업의 미래 계획과 현재 회사 보유 사실을 분리한다. 업로드한 자료는 초안 근거로 쓸 수 있어도 확인된 사실과 동등하게 취급하지 않는다.
2. **평가항목별 작성 계획**: 각 조건을 본문·별도 서식·자격증빙·가격으로 나눈다. 평가 배점에 맞게 페이지를 배분하고 수행 방법·담당자·일정·산출물·검증 방법을 작성한다. 이번의 본문 인용 표는 이러한 업무 분류와 증빙 완료 판정을 대신하지 않는다.
3. **최종 본문 검토와 제한된 보완**: 실제 출력의 누락·모순·회사 주장 전체를 별도 요청에서 검토하고, 문제 페이지만 최대 한 번 보완한 뒤 재검수한다. 지금 입찰의 회사 주장 검토는 작성 계획 중심이며 추가·기존 페이지를 포함한 모든 최종 주장을 검토한 것은 아니다.
4. **실제 공고 검증 세트**: 소규모 교육 용역, IT 구축, 연구 용역 등에서 원문과 최신 변경 공고·회사 증빙을 확보한다. 수동 기준표와 생성 결과를 비교해 누락, 허위 사실, 일정·인력·가격 모순, 글자 잘림을 기록한다. 지정 서식·분량·파일 형식과 실제 PPTX/PDF 출력도 확인한다.

권장 역할 순서는 공고 분석 → 회사 근거 검색 → 평가항목별 설계 → 본문 작성 → 별도 검수 → 출력 검토다.
개인 노트북에서는 Gemma4를 단계마다 순차 호출하고 코드 검사를 함께 사용한다.
동일 모델의 역할 분리는 독립적인 정확성 보증이 아니다. 로컬 품질과 상용 클라우드 품질의 우열은 같은 실제 공고로 비교해야 한다.
클라우드는 필요할 때 선택한 단계만 사용하는 선택 사항이며 현재 무조건 유료로 전환하는 경로는 만들지 않는다.

[조달청의 2026-08-26 발표](https://www.pps.go.kr/kor/bbs/view.do?bbsSn=2608260005&key=00634)도 AI의 요구사항·제안서 분석을 기술평가 보조로 설명하고 최종 판단은 평가위원이 수행한다고 안내한다.
BID3에서 본문 인용이 일치해도 실제 증빙의 진위, 참가 자격, 별도 제출서류, 가격과 최종 평가점수가 확인된 것은 아니다.
현재 버튼의 최종 확정은 사용자가 파일 검토를 완료했다는 작업 상태다. 입찰 제출 가능성 인증을 뜻하지 않는다.

## 검증 기록

- Django 전체 테스트: **276개 통과**. 출력물 인용 대조, 원문 캐시 변경, 소유자 접근, 파일 보존과 동시 수정 충돌을 포함한다.
- 프런트엔드 lint·TypeScript·production build 통과. 초기 Google Fonts 다운로드 실패는 네트워크 복구 후 재시도로 해결했다.
- 실제 **gemma4:26b** 검수: 합성 PPTX 4쪽/요구사항 4개. 30분→30시간, 날짜 변경, 미확인 만족도는 재검토; 명시한 사전·사후 평가와 결과보고 조건은 확인. 예상한 4개 판정과 일치, 약 32초. 이 작은 검증을 실제 입찰 전체 품질 지표로 해석하지 않는다.
- 실제 Tailscale 경로: 기존 소유자 인증으로 13쪽 초안의 최신 파일 대조 HTTP 200, 미인증 요청 HTTP 401. 원본 파일 해시·초안 상태 보존을 확인했다. 공고 요구사항 목록이 없는 기존 초안은 미검수, 남아 있는 확인 필요 문구는 검토 항목으로 표시됐다.
- 브라우저는 로그인 화면 상태여서 로그인 후 신규 표의 시각·클릭 검증은 수행하지 못했다. 인증 API와 웹 빌드는 검증했다. 이번에는 기존 제안서를 새로 생성하거나 실제 입찰에 제출하지 않았다.

개인 파일·검증 JSON·DB·인증 정보는 비공개 `.local/`, `server/media/`에 보관하며 Git에 포함하지 않는다.

## 후속 적용: 회사 근거 보관함

2026-10-09 사용자 계속 진행 요청에 따라 다음 구현 1번의 기본 흐름을 적용했다.

- 기존 `CompanyKnowledgeItem`에 검토 상태, 검토자·시각, 선택 유효기간, 검토 메모와 원문/항목 서명을 추가했다. 기존 데이터는 검토 대기로 유지한다. 실제 회사 자료를 자동 승인하지 않았다.
- 회사정보의 회사 자료 아래에 **회사 근거 보관함**을 연결했다. 문서별 명시적 추출, 분류/상태 필터와 20개씩 페이지 조회, 발췌 확인, 본문 정정, 검토 완료·대기·제외, 인증된 원문 다운로드를 제공한다.
- 회사 자료에 실적·인력·인증 증빙 유형과 PDF 업로드를 추가했다. PDF는 20MB 제한과 패키지 읽기·암호화 검사를 적용한다. 스캔 PDF OCR은 이 변경의 범위 밖이다.
- 검토 완료 저장에는 원문 확인 표시, 출처 위치·발췌, 읽을 수 있는 본인 출처와 현재 항목의 변경 시각이 필요하다. 검토자·시각·서명은 서버가 기록한다. 이전 입력 화면으로 저장하면 충돌로 거절하며, 같은 시스템 시각 안의 저장도 변경 시각을 증가시킨다.
- 유효기간은 지정한 날짜까지 유효하다. 날짜가 지나거나 항목 내용·출처 파일 바이트·저장된 웹페이지 텍스트가 바뀌면 제안서의 검토 완료 근거에서 제외한다. 웹페이지의 실시간 변경을 감시하는 기능은 아니며 기존 홈페이지 수집 주기를 따른다. 원문 변경 시 다시 분석하거나 원문과 사실을 다시 검토해야 한다.
- 제안서 작성과 피드백 수정에 검토 완료·유효한 회사 지식만 제공한다. ID·검토일·유효기간·원문 발췌를 붙이고, 길이 제한을 넘는 항목은 조건을 자르지 않고 전체 제외한다. 회사정보에 직접 입력한 내용은 별도 입력 자료로 유지하며, 검토 완료 증빙으로 승격하지 않는다. 공고의 요구사항이나 과거 제안서 자체가 회사 보유 사실을 증명하지는 않는다.
- 명시적 재분석은 기존 항목과 검토 기록을 새 추출 결과로 대체한다. 기본은 기존 추출 재사용이며 화면에서 재분석을 선택해야 한다. 모든 과거 검토 변경을 별도 이벤트로 영구 보존하는 감사 이력은 아직 구현하지 않았다.
- 동작 범위는 입찰 기능의 회사 근거다. 일반 발표자료 작업실의 별도 참고자료 흐름은 변경하지 않았다. 기존 제안서 파일을 자동 재작성하거나 과거 검수 결과를 회사 증빙의 진위 확인으로 바꾸지 않는다.

검증: Django 전체 **290개**, 프런트엔드 lint·TypeScript·production build, migration 누락 검사 통과. 기존 DB는 비공개 백업 후 마이그레이션했다. 합성 검증 계정의 PDF를 Tailscale 주소로 업로드해 실제 **Gemma4:26b**가 실적·방법론 2개를 추출했다. 약 92초가 걸렸고 자동 추출은 모두 검토 대기, 제안서 회사 지식에서 제외, 다운로드 원문 바이트 보존을 확인했다. 회사 원문·항목 변경 및 만료, 다른 소유자의 목록/검토/분석/다운로드 차단, 출처 없는 승인 거절, 동시 검토 충돌을 자동 검사했다. 웹에서 합성 자료의 발췌·내용 확인과 검토 완료·유효기간 저장 및 상태 필터를 확인했다. 실제 회사 증빙의 진위 심사나 실공고 제안서 전체 재생성 검증은 아니다.

다음 우선순위는 평가항목별 작성 설계와 최종 문서 전체의 회사 주장 검수·제한된 보완이다.
